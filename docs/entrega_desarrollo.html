Entrega técnica para Desarrollo y Base de Datos#

Este documento define cómo conectar, crear o migrar la base del Dashboard de Facturación sin cambiar los resultados que entrega la aplicación. El contrato vigente está compuesto por los modelos SQLAlchemy, los DDL generados y el manifiesto de datos incluidos en este repositorio.

Acceso desde la aplicación#

El documento se consulta dentro de la aplicación desde Ayuda > Entrega a Desarrollo o mediante /entrega-desarrollo. Tanto la vista como las descargas del documento y del manifiesto están habilitadas automáticamente para Full y para usuarios con la autorización puntual permisos_personalizados.entrega_desarrollo = true.

Fuentes autoritativas#

Elemento Fuente
Modelo lógico y reglas de cálculo app/models.py y app/routes.py

Los DDL se generan desde app/models.py; no deben editarse manualmente. Después de cambiar un modelo se ejecuta:

python scripts/generar_esquema_base_datos.py
python scripts/verificar_handoff.py

Configuración sin valores locales fijos#

La aplicación selecciona la base exclusivamente mediante DATABASE_URL. Direcciones, credenciales, año operativo y año base PLP se configuran por ambiente:

APP_ENV=production
SECRET_KEY=<secreto persistente administrado por el ambiente>
DATABASE_URL=postgresql+psycopg://usuario:password@host:5432/facturacion
APP_DEFAULT_YEAR=2026
PLP_BASE_YEAR=2026
NAME_ALIASES_FILE=config/name_aliases.json
CORS_ORIGINS=https://dominio-del-frontend
SESSION_COOKIE_SECURE=1

APP_DEFAULT_YEAR define la selección inicial y no limita los años almacenados. PLP_BASE_YEAR identifica la hoja anual del libro histórico de Personal; las proformas nuevas pueden pertenecer a períodos posteriores. Ninguna ruta local, IP de WiFi o archivo del usuario forma parte del código de producción.

Las jefaturas, segmentos, gerencias, campañas y vigencias operativas provienen de asignaciones_comerciales, administrada desde Datos Maestros. El archivo config/name_aliases.json sólo normaliza variantes de escritura; no asigna la jefatura de una campaña. Si una campaña nueva no tiene asignación, el circuito de Personal informa el faltante y no inventa un responsable.

Esquema y compatibilidad#

Una base nueva contiene 27 tablas. facturacion_anio es multianual; el nombre Python Facturacion2026 se conserva únicamente como alias de compatibilidad y apunta al mismo modelo, no a otra tabla.

La SQLite operativa puede conservar artefactos históricos que la aplicación ya no consulta: la tabla vacía bajas_operativas y algunas columnas antiguas. El migrador omite esos artefactos. Si bajas_operativas tuviera filas, la auditoría la reportaría como tabla extra y la migración debe detenerse para revisión.

Los importes usan NUMERIC, no FLOAT, con la precisión declarada en los DDL. Las fórmulas se calculan en Python a partir de columnas persistidas; no existen triggers ni columnas calculadas ocultas que deban recrearse en PostgreSQL.

Datos que deben migrarse#

Se copian las 27 tablas declaradas, incluidos:

  • usuarios y hashes de contraseña;
  • catálogos, asignaciones y vigencias;
  • facturación y justificaciones;
  • proyecciones, jornadas, precios, variables y tarifaciones;
  • feriados y distribución PLP;
  • proformas e importaciones de seguimiento, incluidos sus BLOB de Excel;
  • historial de cambios y normalizaciones de nombres;
  • tablas de Directorio, dotaciones e indicadores.

Los IDs se preservan porque existen claves foráneas e historial que los referencian. El migrador actualiza las secuencias de PostgreSQL al máximo ID copiado.

Migración recomendada#

  1. Detener escrituras en la aplicación de origen.
  2. Crear un backup consistente de SQLite.
  3. Crear una base PostgreSQL vacía con codificación UTF-8.
  4. Configurar una cuenta temporal con permisos de creación y carga.
  5. Ejecutar el migrador desde el repositorio:
python scripts/migrar_base_datos.py `
  --source-url "sqlite:///C:/ruta/instance/facturacion.db" `
  --target-url "postgresql+psycopg://usuario:password@host:5432/facturacion"

El destino debe estar vacío. El script no borra ni mezcla datos existentes. La copia se ejecuta en transacción, conserva IDs, reinicia secuencias y termina con una comparación de esquema, cantidad de filas y SHA-256 de cada tabla.

Para crear solamente el esquema, un DBA puede ejecutar docs/esquema_base_datos_postgresql.sql y luego usar el mismo migrador sobre las tablas vacías.

Verificación de paridad#

La línea base actual se regenera únicamente cuando una actualización operativa autorizada cambia la fuente:

python scripts/verificar_paridad_bases.py `
  --write-manifest docs/base_actual_manifest.json

Para comparar directamente SQLite y PostgreSQL:

python scripts/verificar_paridad_bases.py `
  --source-url "sqlite:///C:/ruta/instance/facturacion.db" `
  --target-url "postgresql+psycopg://usuario:password@host:5432/facturacion"

Para comprobar una copia de SQLite contra el manifiesto entregado:

python scripts/verificar_paridad_bases.py `
  --source-url "sqlite:///C:/ruta/instance/facturacion.db" `
  --manifest docs/base_actual_manifest.json

El comparador normaliza fechas, booleanos, Unicode y escalas NUMERIC; los BLOB se comparan por tamaño y SHA-256. Nunca imprime la contraseña contenida en una URL de conexión.

Validación funcional posterior#

Con DATABASE_URL apuntando al destino:

python scripts/verificar_entrega.py
python scripts/verificar_handoff.py
python scripts/verificar_matriz_segmentos.py
python scripts/verificar_proforma_seguimiento.py
python scripts/verificar_feriados_facturacion.py
python scripts/verificar_resumen_horas.py

Si se recibe una nueva versión del libro operativo, se concilia contra la solapa anual con este comando. Sin --apply funciona como auditoría y debe informar filas_actualizadas: 0 después de una carga correcta:

python scripts/reprocesar_facturacion_2026.py "RUTA_EXCEL" --year 2026 --apply
python scripts/reprocesar_facturacion_2026.py "RUTA_EXCEL" --year 2026

La asociación usa mes, cliente, servicio y tipo de jornada; no depende de que las horas continúen iguales. Cada aplicación registra el nombre y SHA-256 del archivo en historial_cambios. Las cargas creadas solo en la app se conservan si no existe una fila equivalente en el archivo.

Luego se valida en navegador:

  1. login y permisos;
  2. Datos Maestros y edición de jefatura/segmento;
  3. Resumen por segmento, Resumen por jefatura y Servicios por jefatura;
  4. carga de una proforma en simulación y publicación;
  5. feriado, jornadas laborales y facturación;
  6. edición de Next Gen;
  7. historial y deshacer;
  8. exportaciones de Directorio y Proyectados.

Reglas que deben conservarse#

  • asignaciones_comerciales gobierna jefe, gerente, segmento y vigencia.
  • El bono de Personal es adicional realizado y no integra el objetivo teórico.
  • Las horas planificadas PLP son manuales y se distribuyen en Objetivo Masivo.
  • Los feriados activos recalculan jornadas y horas proyectadas.
  • Una carga mensual PLP reemplaza el mes completo dentro de su alcance.
  • Los importes monetarios se redondean con ROUND_HALF_UP a dos decimales.
  • La Matriz replica el bloque de valor hora del Excel sobre importes agregados:

VH Objetivo = Total Obj / Horas Objetivo, VH Realizado = Total Real / Horas Realizadas y % Valor hora = VH Realizado / VH Objetivo. Total Obj incluye horas y variable objetivo; Total Real incluye horas, variable productivo, bonos y penalizaciones. Tarifación, Next Gen y otros no integran estos cálculos.

  • Las normalizaciones de Proyectados no alteran nombres ni importes de origen.
  • Next Gen conserva la cotización aplicada por producto y mes.

Despliegue#

En producción se usa una sola instancia lógica detrás del proxy o balanceador, una SECRET_KEY persistente y HTTPS. Las migraciones o normalizaciones no deben ejecutarse desde dos procesos simultáneamente. Antes del primer arranque sobre PostgreSQL se aplica el DDL o el migrador; después se inicia la aplicación con una cuenta de ejecución con los permisos mínimos necesarios.

No se versionan .env, logs, bases temporales ni credenciales. Los respaldos de datos reales deben almacenarse en el repositorio de backups definido por el área responsable y no dentro del repositorio de código.

Criterio de aceptación#

  • verificar_handoff.py finaliza con HANDOFF OK.
  • verificar_paridad_bases.py finaliza con PARIDAD OK.
  • No faltan tablas, columnas, índices o claves foráneas.
  • Todas las tablas tienen la misma cantidad de filas y huella SHA-256.
  • Los seis controles funcionales anteriores finalizan sin errores.
  • La aplicación inicia con APP_ENV=production y una clave persistente.
  • Desarrollo conserva el manifiesto y el backup de origen hasta la aceptación.
